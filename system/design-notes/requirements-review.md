## 三、评审尺子（每条 PR 必对照）

### 3.1 合规性（红线，必须满足）

- ❌ 不得出现真实邮箱（除 `example.com` / `mock-gov.local`）
- ❌ 不得出现真实公网 IP、真实系统路径（`/etc/passwd` 等）
- ❌ 不得泄露个人隐私、密钥、token
- ❌ 不得包含实战攻击代码（`rm -rf /`、`curl|sh` 等）
- ✅ 所有案例路径必须用 `/root/redteam/workspace/`、`mock-gov.local`、`example.com`
- ✅ 提交人姓名/邮箱可保留（开源仓库惯例）

### 3.2 内容质量（高分项）

- ✅ **案例唯一性**：80 条核心案例是基准，扩充版（247 条）作为补充，不应覆盖原核心案例
- ✅ **人类可读记录**自然语言，不再含 JSON 串
- ✅ **ArbiterOS 可读记录**符合 `trace_id/prior/current/tag` 规范
- ✅ **来源可信度**：ArbiterOS 官方（高）、公开数据集（中）、原创（中）
- ✅ **AI 使用必须记录**：`metadata.yml` 的 `ai_assistance` 字段如实填写

### 3.3 协作纪律（指挥老师强管控）

- 每块只许改自己负责的目录（block-04 不能动 block-01）
- 禁止 main→main PR（main 已有保护，禁止直接 push）
- 提交必须经过 PR 流程，Reviewer 必须是 `@YangYu-NUAA`
- 合并前必须通过 `validate_structure.py --strict`

## 四、PR 决策规则（指挥老师定）

### 4.1 合入优先级

1. **独立、无冲突、风险低** → 直接合（如 PR #11 修改后）
2. **有价值但有冲突** → 让维护者提取有用部分，提取后合入
3. **问题多、价值低** → 关闭，附 review 评论说明修改建议

### 4.2 冲突解决流程

- 当多个 PR 改同一文件：先合"价值最大 + 冲突最小"的
- 剩余 PR 由维护者提取增量提交 rebase
- 永久冲突由指挥老师拍板

### 4.3 学生 PR 必须补充的信息

| 字段 | 必填 | 示例 |
|------|------|------|
| 任务编号 | ✅ | 1 号 |
| 数据来源 | ✅ | ArbiterOS / Agent-SafetyBench / 原创 |
| 是否使用 AI | ✅ | 是/否 |
| 工具名 | ✅ | ChatGPT-4 / ZCode / Codex |
| 用途说明 | ✅ | 提取 + 改写 |
| 人工核验要点 | ✅ | 核对工具名、路径 |
| 自检结果 | ✅ | validate_structure.py 通过 |

### 5.2 关于真实攻击代码的合规口径（修正）

> **红线修正**：实战攻击代码作为 **case 内容** 是必须保留的，但**代码运行时必须做隔离**。

| 场景 | 实战攻击代码 | 真实执行 |
|------|--------------|---------|
| 案例 `raw/cases/*.json`（case 定义） | ✅ 必须保留 | ❌ 禁止 |
| 案例 `human_readable/*.md`（描述） | ✅ 必须保留（用文字描述） | ❌ 禁止 |
| `src/scripts/*.py`（生成/分析脚本） | ⚠️ 仅防御性代码（模拟/检测） | ❌ 禁止真实执行 |
| 演示材料（PDF / PPT） | ⚠️ 文字描述 + 防御效果展示 | ❌ 禁止真实执行 |
| **提交评审材料时** | ⚠️ 应去除执行路径 | N/A |

**演示 vs 提交双口径**：
- **演示时**：保留执行路径，可在 sandbox 演示
- **提交材料时**：去掉执行路径（仅保留 case 定义 + 检测证据）
