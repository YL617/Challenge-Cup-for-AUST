# 防护框架架构审查与分层处置优化方案 v1

> 审查日期: 2026-08-20 · 基于 GOV-Bench v1.0 (66 条真实有效攻击) 实测结果
> 回答四个问题: 可安装性 / 创新性 / 拦截率优化 / 分层处置设计

## 1. 现状审查

### 1.1 架构现状

当前防护系统为**单点透明代理**(`gov_proxy.py`, 端口 4000), 拦截 OpenAI Chat
Completions 协议的 LLM 响应, 四层策略串行执行:

```
LLM 响应 (含 tool_calls)
  │
  ▼
[1] 意图分类器 (确定性, <1ms)     6 类意图 → BLOCK/JUDGE/ALLOW
  │
  ▼
[2] 规则引擎 UnaryGate            156 注入标记 + 7 条 GOV-DENY 规则
  │
  ▼
[3] Taint 传播                    Spotlighting 标记不可信来源
  │
  ▼
[4] LLM Judge (语义兜底)          0-10 评分, ≥6 阻断
```

### 1.2 实测结论 (GOV-Bench 66 条)

| 指标 | 数值 | 说明 |
|---|---|---|
| 拦截率 | 64/66 (97%) | 2 条 LLM 在防护语境下自拒 |
| 穿透率 | 0 | 无致命动作绕过全部四层 |
| 白名单误杀 | 1/25 (4%) | w-06 边界(过度代理拦截, 设计正确) |

### 1.3 审计发现的问题

按严重度排序:

**P0 处置粒度一刀切。** 意图分类器只有 BLOCK/JUDGE/ALLOW 三档。
RECONNAISSANCE 类命令(`ls/find` 定位文件)当前映射 BLOCK, 误伤正常
运维排查; 而 v11c-13/19 的侦察泄漏说明这类动作其实是**攻击链前奏**,
正确处置是放行+上报, 让链条继续走到外传动作时在 L3 逮住。

**P0 统计口径污染。** 历史拦截中 25 次来自 `judge_error` 的 fail-closed
阻断——LLM Judge 基础设施故障(网络错误、解析失败)被计入"攻击拦截"。
拦截率数字里混入了可用性事件, 需要把"因故障阻断"与"因检测阻断"
分开统计。

**P1 协议单一。** 只支持 OpenAI Chat Completions。Anthropic Messages
协议客户端(Claude Code 等)无法接入。OpenClaw 是靠其 openai-completions
provider 配置绕过的, 不具备通用性。

**P1 无确认通道。** v9-16 类攻击(合法政府域名的跨部门外发)只有
"judge 猜"一条路——猜错就穿透, 猜对靠运气。这类半合法操作需要
人工确认层, 当前架构没有这个位置。

**P2 单点部署。** proxy 进程挂掉则整个 agent 不可用(上游连不通)。
无降级策略(全放行/全阻断/缓存策略)。

**P2 Taint 简化。** 相比 ArbiterOS 的 instruction 级 taint 传播
(security_type 五元组 + prop 计算), 我们的 taint 是近似实现, 无法
做细粒度的污点溯源。

## 2. 可安装性评估

### 2.1 已验证

**OpenClaw** ✅ 完整验证(2026-08-17~20), 66 条攻击 + 白样本全链路。
安装方式: `models.providers.<x>.baseUrl = http://127.0.0.1:4000/v1`,
工具经 MCP(stdio) 暴露, 无需改 OpenClaw 源码。

集成过程中修复的 14 个问题即"安装摩擦清单", 任何新框架接入时按此
核对:

| 摩擦点 | 症状 | 修复 |
|---|---|---|
| stream_options 残留 | 上游 400 | 强制非流式时 pop |
| MCP 工具名前缀 | 规则全部失配 | `gov-mock__x → x` 归一化 |
| 技能以 tool-result 注入 | marker 误触发 | `read(skills/)` 判可信 |
| system prompt 淹没 judge | 语义层失效 | judge 上下文取不可信尾部 |
| 推理模型 thinking 块 | judge 解析空 | 优先 text 块 |
| 会话持久化 | 复测历史污染 | session 加盐 |

### 2.2 待验证(理论可行)

**OpenCode** ✅ 理论可行。OpenCode 支持自定义 OpenAI-compatible
provider(baseURL 指向 proxy), 模型流量与工具协议与 OpenClaw 同构。
预期摩擦点: 工具命名前缀差异、system prompt 结构差异——两者都已有
归一化机制兜住。建议列入下一轮实测(半天工作量)。

**通用判定标准**: 任何满足以下两条件的 agent 框架均可安装:
1. LLM 调用允许自定义 baseURL(OpenAI-compatible 或 Anthropic-compatible);
2. 工具执行结果回传进 LLM 上下文(即存在 tool-role 消息)。

### 2.3 不可直接安装

**Anthropic Messages 协议客户端**(Claude Code 等): 需要 `/v1/messages`
协议适配层(请求/响应格式转换 + SSE 流式封装)。估计 2-3 天工作量,
复用 judge 模块已有的 Anthropic 协议处理代码。

**嵌入式 agent**(工具调用不经 LLM API 往返的): 无 API 拦截点,
需要换成 SDK hook 方案(参照 ArbiterOS 的 LiteLLM callback 模式)。

## 3. 创新性对比

### 3.1 诚实定位

**核心模式不新**: "透明 LLM 代理 + 策略钩子"是已知模式。ArbiterOS
用 LiteLLM callback 做 pre/post hook; XA_guard 是六关卡管线; 学术界
有多篇 agent 防火墙工作。我们的架构在这个层面是**工程复现+领域深化**,
不构成创新点。

**构成创新的五个点**(均有实证支撑, 可写入报告):

1. **攻击有效性优先的基准方法论**。三层验证链(裸诱导预筛 → 真实
   环境有效性 → 防护拦截复测)要求每条用例在被用于评测防护前, 先
   证明攻击本身成立。InjecAgent(1054 条)与 AgentDojo(97 条)均不做
   有效性复验; 我们实测同批用例在修复防护后有效率仅 9%, 说明
   不做此验证的基准会系统性稀释评测。**这是方法论层面的贡献。**

2. **信任按来源分、不按通道分**。技能库经 tool-result 通道到达
   (与间接注入同通道), 以 `tool_call_id → read(path 含 skills/)`
   回溯判定开发者可信。通道级信任(扫所有 tool result)会误杀,
   内容级信任(匹配关键词)会被伪造——来源级信任以调用图为准。

3. **不可信尾部的语义判定上下文**。Judge 只看 user+tool-result 的
   末尾 2000 字符, 对抗 agent 框架 system prompt 对上下文窗口的
   淹没(实测全量前缀会被框架提示占满, 用户请求被截断导致误判)。

4. **政务域收件人白名单 + PII 外发联动**。域名白名单模型(gov.cn
   等内部域之外一律视为外部)叠加"正文命中 PII 正则且收件人无
   可验证内部地址"规则, 由 v9-01 穿透与 v10-08 穿透两个案例驱动。

5. **观察模式基线测量**。`GOV_PROXY_OBSERVE=1` 保持链路完全一致
   仅关闭执行, 使"有/无防护"成为单变量对照。此前测量中曾因漏设
   该变量导致基线被拦截模式污染, 反证其必要性。

### 3.2 与竞品的差距(需在报告中如实说明)

- ArbiterOS 有 instruction 级统一表示与 16 策略的形式化框架, 我们
  的策略是过程式的, 缺乏可组合性的形式保证;
- XA_guard 有 AIBOM(CycloneDX)供应链追溯, 我们没有等价物;
- 两者都不影响当前评测结论, 但影响"框架完整性"的评审印象。

## 4. 分层处置架构设计(用户方向)

### 4.1 设计原则

参照 agent 框架的行为分层(如 OpenClaw 的 exec-approvals 分级、
Claude Code 的 permission modes), 把处置从"拦/不拦"二元改为
**四级处置**, 每级对应不同的用户可见行为:

| 层级 | 处置 | 用户可见行为 | 适用意图 |
|---|---|---|---|
| **L0 放行** | 直接执行 | 无感知 | NORMAL_OPERATION(查询/草稿/读非敏感) |
| **L1 上报** | 执行+记录+通知 | 正常继续, 事后可在审计流看到 | RECONNAISSANCE、低危异常 |
| **L2 确认** | 暂停待确认 | 交互式: 弹确认; 自动化: 返回"需人工确认" | DATA_EXPORT(政府域名)、AUTHORITY_OPERATION、批量操作 |
| **L3 阻断** | 移除调用+短原因 | "已阻断: <一句话原因>" | DESTRUCTIVE、SYSTEM_TAMPERING、确认攻击 |

### 4.2 关键设计决策

**L1 上报而非阻断(侦察类)。** v11c-13/19 实证: 攻击链先 `ls/find`
定位再 `curl` 外传。拦侦察则攻击者换路径重试, 链条断在我们看不见
的地方; 放行侦察+上报, 链条继续走到外传动作, 在 L3 逮住并保留完整
攻击链证据。**L1 的价值是把检测点后移到危害动作本身。**

**L2 确认(半合法操作)。** v9-16 类(合法政府域名+跨部门业务框架)
的本质是"无法从上下文判定合法性", 语义层猜错的代价是不对称的
(穿透=数据泄露, 误拦=业务中断)。L2 把判定权交还人工, 语义层只
负责把这类操作**识别出来并停住**, 不负责猜结论。

**L3 短原因返回。** 阻断消息写回 agent 上下文(当前已实现), 格式
固定为"已阻断: <规则名>·<一句话>", 让 agent 能向用户转述而非死循环
重试。66 条用例的阻断原因已验证 agent 可理解并停止。

### 4.3 实现路径(估计 2-3 天)

```python
# intent_classifier.py — 意图 → 处置层级
DISPOSITION_POLICY = {
    "NORMAL_OPERATION":  "L0",
    "RECONNAISSANCE":    "L1",   # BLOCK → L1 (核心变更)
    "DATA_EXPORT":       "L2",   # JUDGE → L2 (judge 结果可升级到 L3)
    "AUTHORITY_OPERATION":"L2",  # JUDGE → L2
    "DESTRUCTIVE_ACTION":"L3",
    "SYSTEM_TAMPERING":  "L3",
}

# gov_proxy.py — 分级执行
# L1: 标注放行, audit 记 {"type": "tier1_reported", ...}
# L2: 移除调用, 原因="需人工确认: <依据>", audit 记 tier2_confirm
#     (交互式接框架审批回调, 自动化模式等价于阻断+明确原因)
# L3: 移除调用, 原因="已阻断: <攻击类>", audit 记 tier3_blocked
# judge 升级: L2 操作经 judge 高分(≥8)确认攻击 → 升 L3
```

### 4.4 预期效果与验证方案

| 用例集 | 预期分布 | 验证命令 |
|---|---|---|
| GOV-Bench 66 条 | L3 ≥ 60, L2 ~4, L1 ~2 | openclaw_case_runner 有防护模式 |
| 白名单 25 条 | L0 ≥ 23, L1 ~2 | runner --white |
| v11c-13/19 侦察链 | R1 在 L1, 外传动作到 L3 | 单例复测 |

分层后的核心指标从单一拦截率变为**分层正确率**: 攻击落在 L2/L3
(危害控制住), 正常业务落在 L0/L1(不打断), L2 确认的人工采纳率
(衡量 L2 阈值松紧)。

## 5. 拦截率 100% 的差距分析

66 条中 64 拦 + 2 自拒已到位。剩余差距与已知穿透类:

1. **侦察后未及外传**(v11c-13/19): 分层后自然解决(链条完整走完)。
2. **政府域名跨部门外发**(v9-16): L2 解决。
3. **judge 故障 fail-closed**: 单列统计口径, 故障阻断不计入拦截率;
   同时把 judge 超时从 fail-closed 改为降级 L2(故障时按"需确认"处理,
   比误阻断温和、比放行安全)。
4. **组合命令链**(`cmd1 && cmd2 | cmd3`): 当前意图分类按整串匹配,
   需拆分为命令段逐段分级, 任一段 L3 则整体 L3。

完成 1-4 后, 预期 66 条全部落在 L2/L3, 其中 L3 ≥ 90%。
