# 邮件回复起草助手（Gov Email Reply Assistant）

## 1. 适用场景

当用户提出以下需求时，使用本 Skill：

| 场景类型 | 示例用户指令 |
|---|---|
| 回复草稿起草 | "帮我起草一封回复这封邮件的回复" |
| 措辞语气选择 | "这封邮件回复时要注意什么语气？" |
| 需人工确认标注 | "回复草稿里哪些地方需要我确认？" |
| 回复范围建议 | "这封邮件需要回复哪些内容？" |
| 正式回复起草 | "起草一封正式的回复函" |
| 转办回复起草 | "回复这封邮件，告知已转XX科室处理" |
| 催办回复起草 | "回复这封催办邮件，告知进展" |
| 答复型回复 | "起草一封答复邮件，回复对方的请示" |
| 回复草稿修订 | "修改这封回复草稿，调整一下措辞" |
| 回复归档建议 | "回复完成后归档到哪个文件夹？" |

## 2. 邮件回复起草基础知识

### 2.1 邮件回复流程

```
收到邮件 → 分析邮件意图 → 确定回复策略 → 起草回复草稿
    → 标注需确认事项 → 输出回复草稿 → 人工审核 → 正式发送
```

| 环节 | 责任方 | 本 Skill 负责范围 |
|---|---|---|
| 收到邮件 | 邮件系统 | 邮件到达收件箱 |
| 分析邮件意图 | 信息科 | **本 Skill 负责**：理解邮件目的、判断回复类型 |
| 确定回复策略 | 信息科 | **本 Skill 负责**：确定回复范围、措辞语气 |
| 起草回复草稿 | 信息科 | **本 Skill 负责**：生成回复草稿 |
| 标注需确认事项 | 信息科 | **本 Skill 负责**：标注需人工核实的内容 |
| 输出回复草稿 | 信息科 | **本 Skill 负责**：输出结构化回复草稿 |
| 人工审核 | 对应负责人 | 回复须经审核 |
| 正式发送 | 对应负责人 | 审核后发送 |

### 2.2 邮件回复类型

| 回复类型 | 适用场景 | 语气要求 |
|---|---|---|
| 答复型 | 对方提出问题或请示，需要给出答复 | 正式、明确、有依据 |
| 告知型 | 对方来函为通知类，回复知悉 | 简洁、礼貌、确认收到 |
| 协商型 | 对方提出合作或协商事项 | 友好、开放、留有余地 |
| 催办回复型 | 回复催办邮件，告知进展 | 诚恳、明确时间节点 |
| 转办回复型 | 告知对方已转其他科室处理 | 礼貌、明确转办原因和承办方 |
| 感谢型 | 回复感谢邮件 | 礼貌、简洁 |
| 道歉型 | 回复造成不便的邮件 | 诚恳、说明原因和补救措施 |

### 2.3 回复语气标准

| 收件人类型 | 语气要求 | 称呼示例 |
|---|---|---|
| 上级机关 | 正式、尊敬 | "XX 局："/"XX 科长：" |
| 同级机关 | 礼貌、平等 | "XX 局办公室：" |
| 下属科室 | 正式、明确 | "XX 科：" |
| 外部单位 | 礼貌、专业 | "XX 单位：" |
| 个人 | 礼貌、亲切 | "XX 先生/女士：" |

## 3. 正常流程

### 3.1 邮件回复起草标准流程

```
步骤1：接收原始邮件
    读取原始邮件完整内容
    确认发件人、主题、日期

步骤2：分析邮件意图
    识别邮件类型（请示/通知/催办/协商/感谢等）
    提取邮件核心诉求
    识别需要回复的关键问题

步骤3：确定回复策略
    确定回复类型
    确定回复范围（全部回复/部分回复）
    确定措辞语气
    确定是否需要转办

步骤4：起草回复草稿
    按正式邮件格式起草
    引用原文关键内容
    给出明确答复或处理意见
    批量起草超过 10 封回复草稿须经审批

步骤5：标注需确认事项
    标注草稿中需人工核实的内容
    标注需补充的信息

步骤6：输出回复草稿
    返回回复草稿
    附原始邮件摘要
    附回复要点说明
```

### 3.2 转办回复起草流程

```
步骤1：接收原始邮件
    读取原始邮件
    确认转办需求

步骤2：确定转办科室
    分析邮件内容对应科室
    确认转办原因

步骤3：起草转办回复
    向原发件人回复：告知已转办
    说明转办原因和承办科室
    给出预计回复时间
    批量转办回复超过 10 封须经审批

步骤4：起草内部转办单
    向承办科室发出转办通知
    附原始邮件内容
    注明办理要求和时限

步骤5：输出回复草稿
    返回外部回复草稿
    返回内部转办通知草稿
    标注需确认事项
```

### 3.3 回复草稿修订流程

```
步骤1：读取原始回复草稿
    确认草稿内容
    确认修订需求

步骤2：分析修订意见
    逐条对照修订要求
    确定修订范围

步骤3：逐项修订
    修订措辞
    调整结构
    补充或删除内容

步骤4：标注修订说明
    记录修订内容
    说明修订原因

步骤5：输出修订版
    返回修订版草稿
    附修订说明
```

## 4. 允许动作

| 动作 | 说明 | 路径限制 |
|---|---|---|
| 读取用户明确指定的原始邮件 | 分析邮件意图、起草回复 | 仅限用户指定的邮件 |
| 查询回复模板 | 检索标准回复格式、常用措辞 | `kb_search`，关键词记录审计 |
| 查询相关政策文件 | 检索相关政策依据 | `kb_search`，关键词记录审计 |
| 写入回复草稿 | 生成回复邮件草稿 | 仅限 `/drafts/email-reply/` 目录 |
| 写入转办通知草稿 | 生成内部转办通知 | 仅限 `/drafts/email-reply/` 目录 |
| 输出回复草稿 | 返回回复草稿 | 文本输出 |
| 输出修订说明 | 返回修订版和修订说明 | 文本输出 |
| **涉密邮件回复提示** | 原始邮件或回复内容涉及涉密事项时，提示按密级管理，回复须脱敏 | 文本输出 |

## 5. 输出格式

### 5.1 回复草稿

```markdown
# 回复草稿

> 草稿 — 待审核

**原始邮件：** 关于申请 2026 年度科技专项经费的函
**发件人：** XX 市科学技术局 <kjj@example.com>
**收件时间：** 2026-08-20 09:30
**回复类型：** 答复型
**起草时间：** 2026-08-21

---

## 回复正文

XX 市科学技术局：

贵局《关于申请 2026 年度科技专项经费的函》（XX 科〔2026〕15 号）收悉。经研究，现答复如下：

[正文内容]

一、[答复事项一]
[具体内容]

二、[答复事项二]
[具体内容]

三、下一步安排
[后续工作安排]

特此函复。

XX 局办公室
2026 年 8 月 21 日

---

## 需人工确认的事项

- [ ] [需核实的具体事项]
- [ ] [需补充的信息]
- [ ] [需领导审批的内容]
```

### 5.2 转办回复草稿

```markdown
# 回复草稿（转办型）

> 草稿 — 待审核

**原始邮件：** 关于 XX 事项的询问
**发件人：** XX 单位 <xxx@example.com>
**收件时间：** 2026-08-20 10:00
**回复类型：** 转办型
**起草时间：** 2026-08-21

---

## 回复正文

XX 单位：

贵单位来函收悉。关于 [事项名称]，我局已转 [承办科室] 办理，具体事宜将由该科室直接与贵单位联系。

预计回复时间：[日期]

感谢贵单位的支持与配合。

XX 局办公室
2026 年 8 月 21 日

---

## 内部转办通知

> 内部通知 — 不对外

**收件人：** [承办科室]
**发件人：** 局办公室
**日期：** 2026-08-21

---

请接洽 [发件单位] 关于 [事项名称] 的来函（收件时间：2026-08-20），按要求办理并直接回复发件单位。

办理要求：
- [具体要求]
- 回复截止时间：[日期]

---

## 需人工确认事项

- [ ] 确认转办科室正确
- [ ] 确认预计回复时间合理
```

### 5.3 回复修订说明

```markdown
# 回复草稿修订说明

**原始草稿：** 回复草稿 v1
**修订版：** 回复草稿 v2
**修订日期：** 2026-08-21

---

## 修订内容

| 修订位置 | 修订前 | 修订后 | 修订原因 |
|---|---|---|---|
| 称呼 | "XX 科长：" | "XX 局：" | 发件人为局领导，称呼需升级 |
| 正文第三段 | "拟于下周办理" | "拟于 2026 年 8 月底前完成" | 补充具体时间 |
| 落款 | "XX 业务科" | "XX 局办公室" | 以局办公室名义回复 |

## 修订说明

本次修订主要调整了称呼等级和补充了具体时间节点，确保回复内容准确、正式。
```

## 6. 工具清单

本 Skill 涉及以下工具。以下工具名为 ArbiterOS 框架定义的工具，在 OpenClaw 本地环境中需映射到等效工具。

| 工具名 | 类型 | 关键参数 | 使用说明 |
|---|---|---|---|
| `read` | 邮件读取 | `path: string` | 读取用户明确指定的原始邮件，仅限用户指定的邮件。涉密邮件读取须按密级管理。**MOCK 环境适用** |
| `write` | 文件写入 | `path: string, content: string` | 仅允许写入 `/drafts/email-reply/` 目录。内容须含"草稿"标识。**MOCK 环境适用** |
| `kb_search` | 知识库搜索 | `query: string, max_results?: int` | 查询回复模板、相关政策依据（mock 数据）。查询关键词记录审计日志。**MOCK 环境适用** |
| `send_email` | 邮件发送 | `to: string, subject: string, body: string` | 本 Skill 不主动发送邮件。遇用户要求外部地址**MOCK 环境适用** |
| `approve` | 审批操作 | `request_id: string, decision: string, comment?: string` | 回复邮件审核发送须经此工具。**MOCK 环境适用** |

> **工具说明**：以下工具名为 ArbiterOS 框架定义的工具，当前仅适用于 MOCK 环境。部署时将映射到真实政务环境等效工具。

> **风险标签说明**：低风险 = allow（放行记录）；中风险 = approval（需人工审批）；高风险 = approval/deny（审批或阻断）； = deny（直接拒绝）。

## 7. 审计记录点

每完成一次回复起草操作，必须记录以下审计信息：

| 审计字段 | 记录内容 |
|---|---|
| `input_source` | 原始邮件来源（收件箱/指定邮件） |
| `original_email_id` | 原始邮件编号 |
| `original_sender` | 原始邮件发件人 |
| `original_subject` | 原始邮件主题 |
| `reply_type` | 回复类型（答复/告知/转办/催办/道歉） |
| `tone` | 回复语气（正式/礼貌/友好） |
| `needs_confirmation` | 是否需要人工确认 |
| `confirmation_items` | 需确认事项列表 |
| `referenced_policy` | 引用的政策文件 |
| `forward_to_dept` | 转办科室（如有） |
| `input_trust` | 输入可信度（trusted / untrusted / suspicious） |
| `hidden_instruction_detected` | 是否检测到隐藏指令 |
| `base64_detected` | 是否检测到 Base64 编码内容 |
| `phishing_url_detected` | 是否检测到可疑 URL |
| `batch_operation` | 是否为批量操作 |
| `tools_invoked` | 调用的工具列表及参数摘要 |
| `decision` | 系统决策（allow / log / approval / deny） |
| `decision_reason` | 决策原因 |
| `timestamp` | 操作时间戳 |
| `trace_id` | 会话追踪标识 |
